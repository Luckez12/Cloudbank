# VidSrc v3.2.0 — frame-local Play flow

The current website's outer embed fetches its iframe URL dynamically. The nested poster page has `autoStart=false`; its `button#bigPlay` listener creates `iframe#player_frame`. The actual player then handles verification, API access, decoding and HLS loading. Previous provider timers attempted top-document interactions and coordinate touches. The final click delay equaled the provider timeout and was never scheduled; no further interaction followed the six-second tick.

This provider opts into a generic VUEO frame-interaction capability. A document-start script runs inside each frame, waits for document readiness and activates only the explicitly selected media Play button. It observes late DOM changes instead of relying on top-document access to cross-origin iframe DOM. It stops observing the poster document when the actual player iframe appears. The native coordinate-click path is disabled in this opt-in mode.

The app accepts only named button/iframe ID or class selectors, keeps bounded frame-event counters and tracks provider-selected request path prefixes without logging URL queries or response bodies. Default behavior for providers that do not request this feature remains unchanged. The script does not click verification widgets, alter tokens, call a separate API or bypass website verification. WebView document-start injection support is required; `hook=false` reports lack of installation support instead of pretending Play occurred.

New logs report hook installation, ready frame count, Play click count, actual player iframe count, bootstrap/player/API request counts and any observed API HTTP error. API counts include metadata requests; they do not alone prove the stream API succeeded. These stages are observations, not playback verification. Missing bridge support is explicitly identified.

The provider still returns captured media with original URLs/headers and adaptive Auto quality. No native media validation, binary transport, separate API/token replay, master splitting, child/segment request or subtitle request is added. It requests a 12-second maximum with a 300 ms finish delay after media capture; this is a ceiling, not a measured device speed claim.

Verification: provider fixtures pass for exact movie/episode routes, frame-interaction options, original master/header handoff, basic and detailed result formats, zero native HTTP calls and empty results. Frame-script fixtures pass for DOM readiness, an iframe Play button appearing after six seconds, separate frame contexts, one successful activation, player creation, cleanup and content-free diagnostics. The full modified resolver and its existing session policy compile against Android API 35 and AndroidX WebKit 1.14.0. A full APK and real Android WebView playback have not been tested here.

Apply the separate VUEO frame-interaction ZIP and build/install the app, then apply this Cloudbank-only ZIP and refresh the provider. Both patches are required for the intended interaction flow. Existing generic binary support is unrelated and need not be removed. Manifest v1.20.80, VidSrc v3.2.0. The existing delete list remains UHDMovies, VegaMovies and VidEasy; VidLink stays deferred.
