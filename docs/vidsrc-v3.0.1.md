# VidSrc v3.0.1 — match current website requests

The supplied v3.0.0 device log reaches the stream API after four requests and is rejected with HTTP 403 before loading a decoder. This is an API rejection, not evidence of an app binary decoding failure. The response body was not logged, so its exact reason on that device is unknown.

The v3.0.0 HTTP implementation omitted the player Origin on cross-origin API/WASM requests. It also serialized URLSearchParams to add the token, rewriting the website's bare `stream_urls` parameter as `stream_urls=`. Its cache headers differed from the normal no-cache form generated by the website's fetch flow. These request differences are corrected; the API/WASM requests carry the player Origin, the API Referer is the player origin, and the website's query is preserved when appending the fresh token.

A new manual HTTP audit with the player Origin and no-cache headers received HTTP 200 with encrypted stream data. This supports matching the website more closely; it does not isolate which difference caused a prior rejection or prove reliable API access, device speed or playback. Earlier audits included an API `invalid api token` response and media-host HTML 403. No playback success is claimed.

API errors now log only a small classified reason (`invalid-api-token`, `expired-token`, or `verification-required`) when the server provides one. Tokens, IPs, full API responses and signed media URLs are never printed. No retry loop, fallback browser or additional media checks were added.

Tests verify Origin for both API and native WASM requests, exact bare query flag preservation, cache headers, sanitized API rejection, movie/TV identity, public decoder caching and the decoder's agreement with the downloaded website WASM. Repository validation passes with 36 providers.

This is a Cloudbank-only patch: manifest v1.20.78 and VidSrc v3.0.1. The previously supplied generic VUEO binary transport update is still needed for remote WASM responses; there is no new app change. The existing delete list remains UHDMovies, VegaMovies and VidEasy. Master HLS URLs are returned unchanged, with no master/child/segment/subtitle probe.
